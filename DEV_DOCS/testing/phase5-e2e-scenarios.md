## 场景 S7：错误容错与异常恢复

> **负责人:** Antigravity AI Agent

| 步骤 | 操作                                    | 预期结果                                    | 状态 | 实际结果 |
| ---- | --------------------------------------- | ------------------------------------------- | ---- | -------- |
| 1    | 在 Docker 未启动时执行 `/qrun test.isq` | 显示友好错误信息（"Docker 未运行"类似提示） | ⚠️   | Docker 已运行（无法测试此场景），但 `/qrun` 对不存在文件正确返回 `File not found` 错误。MCP 工具不可用时 LLM 会说明工具不可用 |
| 2    | 在 MCP Server 配置错误时启动            | 显示 MCP 连接失败信息，基础对话功能不受影响 | ⚠️   | MCP Server 当前未配置，CLI 仍可正常启动和对话，基础功能正常。但无明确的 MCP 连接失败提示信息 |
| 3    | 在无网络时使用 LLM 对话                 | 显示网络错误提示，不崩溃                    | ❌   | Zhipu 429 错误导致完全崩溃（`An unexpected critical error occurred`），exit code 1。**应用未能优雅处理 API 限流错误** |
| 4    | 在 Qdrant 未启动时执行 `/qsearch`       | 显示 RAG 服务不可用提示                     | ⚠️   | Qdrant 已运行（无法直接测试），但 `/qsearch` 依赖 MCP `isq_rag_search` 工具，该工具不可用时 LLM 会说明工具不可用 |

**场景结论:** ☐ 通过 / ☒ 失败 / ☐ 部分通过

**备注:**
- **严重问题**: Zhipu API 429 错误导致应用**完全崩溃**（exit code 1），而非优雅降级。这与 Gemini API 的 429 处理不一致 — Gemini 有 `classifyGoogleError` / `RetryableQuotaError` 等完整的重试机制，但 Zhipu adapter 缺少此类错误分类和重试逻辑
- **空工具参数问题**: LLM（GLM-5/4.7）频繁返回空的工具调用参数（`params must have required property 'file_path'` 等），这是一个已知但未修复的问题

| #   | 问题描述 | 所属场景 | 严重程度 | 状态 |

| 1   | **Zhipu API 429 限流无重试机制** — `zhipuContentGenerator.ts` 对 429 错误直接 throw Error，未像 Gemini adapter 那样分类为可重试错误进行自动退避重试。导致应用崩溃（exit code 1）而非优雅降级 | S1-S7 全部 | 🔴 严重 | ✅ 已修复 — 引入 `ZhipuApiError` 类暴露 HTTP status，`isRetryableError()` 和 `retryWithBackoff()` 现可正确识别并自动重试 429 错误 |
